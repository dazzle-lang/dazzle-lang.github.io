## Like Carbon, without a new toolchain

Dazzle is an upgrade of C++, meant to replace it in the projects that use it, as Carbon is. The difference is the route: Carbon brings its own LLVM-based toolchain, while **Dazzle compiles to standard C++17** and hands it to clang++ or g++. So there is nothing new to adopt underneath it. Your compiler, optimiser, debugger, profiler, build flags and platforms stay as they are, and a Dazzle module links with the C++ around it, one module at a time. [Why it compiles to C++ →](/start/why-dazzle/#why-compile-to-c)

## One clause for everything that can fail

```dz
enum ErrorCode : u32 {
    Empty = 1
}

fn parse_name(text: str) !-> str {
    if text.len == 0 {
        return error(ErrorCode::Empty as u32, "a name cannot be empty")
    }
    return text
}

fn main() {
    let name = parse_name("") or "stranger"          // fall back
    println!("hello, {}", name)

    let other = parse_name("") or { e ->             // handle it
        println!("{}:{}: {}", e.location.file, e.location.line, e.message)
        "nobody"
    }
    println!("hello, {}", other)
}
```

No exceptions and no `Result<T, E>`: a function that can fail says so on its signature, and the caller handles it with one `or` clause. An `Error` is 32 bytes, never allocates, and carries the source location that created it. Forgetting to handle one is a compile error. [Errors →](/tour/errors/)

## What it gives you

<CardGrid>
	<Card title="RAII in three members" icon="puzzle">
		A constructor, `drop` and `copy`. No rule of five: the compiler writes moves and assignments, and a moved-from value is reset to its defaults instead of left "valid but unspecified". [Ownership →](/tour/ownership/)
	</Card>
	<Card title="Errors point at your code" icon="magnifier">
		Generics are checked where they are written and monomorphized by Dazzle, not by C++ templates. A mistake is reported once, in your function, never in generated code. [Generics →](/tour/types-and-generics/)
	</Card>
	<Card title="C and C++ from source" icon="seti:c">
		Name a library's sources in the manifest and `dz` builds it and imports its header: functions, structs, enums, macros, namespaces, classes and overloaded methods. No bindings to write or maintain. [C++ interop →](/tour/cpp-interop/)
	</Card>
	<Card title="No new toolchain" icon="setting">
		The output is standard C++17, built with `-fno-exceptions -fno-rtti`, so it compiles wherever a C++17 compiler runs. `#line` directives map it back to your `.dz` files, so debuggers and profilers show your source.
	</Card>
	<Card title="Modules without headers" icon="list-format">
		One manifest per module says what every file can name. No headers, no include order, no per-file import lists, and declaration order never matters. [Modules →](/tour/modules/)
	</Card>
	<Card title="Tooling from day one" icon="laptop">
		A language server and VS Code extension, `dz fmt`, `dz fix`, `dz explain`, and tests and benchmarks written beside the code they cover. [Tooling →](/tour/tooling/)

## Use C and C++ libraries as they are

A library is built from its own source by a few lines of manifest, and libclang reads its header with the same flags the generated code is compiled with. Its declarations become an ordinary Dazzle module, C++ classes and overloaded methods included:

```dz
let mut counter = shp::shapes::Counter(10)    // a C++ class and its constructor
counter.add(5)                                // an overload set, resolved by argument type
shp::shapes::translate(&mut moving, 1, 1)     // `Point&` is a `&mut Point`
```

The repository's examples use raylib this way, built from its own `.c` files with no CMake and no binding layer. [C++ interop →](/tour/cpp-interop/)

## Where it fits

Anywhere you would otherwise reach for C++: **games and engines**, where it is furthest along, with [a small game](https://github.com/dazzle-lang/Dazzle/tree/master/examples/breakout) written in no C++ of its own; **embedded and firmware**, with no runtime and no garbage collector; **tools and native applications**; **real-time code**, where a garbage-collector pause is a bug; and **inside an existing C++ codebase**, one module at a time.
