## Bugs C++ lets through

These are eight mistakes that both g++ and clang++ compile. Half of them compile without a single warning on either compiler, even with `-Wall -Wextra`. In Dazzle, each one is a compile error or has one defined meaning:

<div class="dz-bugs not-content">

| The mistake | C++ | Dazzle |
|---|---|---|
| Using a value after `std::move` | compiles, reads whatever is left | <span class="ok">error DZ0401</span> |
| Ignoring a returned error | compiles silently | <span class="ok">error DZ0510</span> |
| A `switch` missing an enum value | compiles; that value does nothing | <span class="ok">error DZ0513</span> |
| Falling off the end of a function | undefined behaviour, with a warning | <span class="ok">error DZ0405</span> |
| Signed overflow | undefined, `x + 1 < x` folded to `false` | <span class="ok">wraps, in every build</span> |
| Order of evaluating arguments | unspecified: g++ and clang disagree | <span class="ok">left to right</span> |
| Reading an uninitialised variable | undefined behaviour | <span class="ok">every value is initialised</span> |
| Indexing past the end of an array | undefined behaviour | <span class="ok">checked in every build</span> |

</div>

Each diagnostic points at the line, says what is wrong there, and ends with a help line:

</div>

## One clause for everything that can fail

```dz
enum ErrorCode : u32 {
    Empty = 1
}

fn parse_name(text: str) !-> str {
    if text.len == 0 {
        return error(ErrorCode::Empty as u32, "a name cannot be empty")
    }
    return text
}

fn main() {
    let name = parse_name("") or "stranger"          // fall back
    println!("hello, {}", name)

    let other = parse_name("") or { e ->             // handle it
        println!("{}:{}: {}", e.location.file, e.location.line, e.message)
        "nobody"
    }
    println!("hello, {}", other)
}
```

<Terminal snippet="fallback" />

There are no exceptions and no `Result<T, E>`. A function that can fail says so in its signature, and the caller handles the failure with one `or` clause. An `Error` is 32 bytes, never allocates, and carries the source location that created it. Forgetting to handle one is a compile error. [Errors →](/tour/errors/)

## What it gives you

<CardGrid>
	<Card title="RAII in three members" icon="puzzle">
		A constructor, `drop` and `copy`. There is no rule of five: the compiler writes moves and assignments, and a moved-from value is reset to its defaults instead of left "valid but unspecified". [Ownership →](/tour/ownership/)
	</Card>
	<Card title="Errors point at your code" icon="magnifier">
		Generics are checked where they are written and monomorphized by Dazzle, not by C++ templates. A mistake is reported once, in your function, never in generated code. [Generics →](/tour/types-and-generics/)
	</Card>
	<Card title="C and C++ from source" icon="seti:c">
		Name a library's sources in the manifest, and `dz` builds it and imports its header: functions, structs, enums, macros, namespaces, classes and overloaded methods. There are no bindings to write or maintain. [C++ interop →](/tour/cpp-interop/)
	</Card>
	<Card title="Standard C++17 out" icon="setting">
		The output is plain C++17, built with `-fno-exceptions -fno-rtti`, so it compiles wherever a C++17 compiler runs. `#line` directives map it back to your `.dz` files, so debuggers and profilers show your source. [Why C++? →](/start/why-dazzle/#why-compile-to-c)
	</Card>
</CardGrid>

## Use C and C++ libraries as they are

A few lines of manifest build a library from its own source. libclang reads its header with the same flags the generated code is compiled with. Its declarations become an ordinary Dazzle module, C++ classes and overloaded methods included:

```dz
let mut counter = shp::shapes::Counter(10)    // a C++ class and its constructor
counter.add(5)                                // an overload set, resolved by argument type
shp::shapes::translate(&mut moving, 1, 1)     // `Point&` is a `&mut Point`
```

Every example in the gallery above works this way: raylib, SDL3, Box2D, sokol, stb and RGFW, each built from its own source. [C++ interop →](/tour/cpp-interop/)

## Where it fits

You can use Dazzle anywhere you would otherwise reach for C++:

- **Games and engines.** This is where it is furthest along.
- **Embedded and firmware.** There is no runtime and no garbage collector.
- **Tools and native applications.**
- **Real-time code**, where a garbage-collector pause is a bug.
- **An existing C++ codebase**, one module at a time.
