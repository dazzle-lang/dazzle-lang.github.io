## The idea

C++ gives you control and abstraction, and buries both under forty years of syntax and undefined behaviour. The languages that strip C++ down give back the clarity, and take away what a large codebase is built from: RAII, encapsulation, and layers of abstraction that hold up. Dazzle keeps all of that and changes the rest.

## Bugs C++ lets through

Here are ten of the mistakes that both g++ and clang++ compile. Seven of them compile without a single warning on either compiler, even with `-Wall -Wextra`, and the first eight are undefined behaviour. In Dazzle, each one is a compile error or has one defined meaning:

<div class="dz-bugs not-content">

| The mistake | C++ | Dazzle |
|---|---|---|
| Indexing past the end of an array | undefined behaviour | <span class="ok">checked in every build</span> |
| Reading an uninitialised variable | undefined behaviour | <span class="ok">every value is initialised</span> |
| Using a pointer that may be null | undefined behaviour, no warning | <span class="ok">error DZ0528</span> |
| Copying a struct that owns memory | double free, no warning | <span class="ok">error DZ0403</span> |
| Signed overflow | undefined, `x + 1 < x` folded to `false` | <span class="ok">wraps, in every build</span> |
| Dividing by zero | undefined, no warning | <span class="ok">panics, naming the line</span> |
| Falling off the end of a function | undefined behaviour, with a warning | <span class="ok">error DZ0405</span> |
| Keeping a reference across a `push_back` | undefined behaviour, no warning | <span class="ok">error DZ0413</span> |
| Using a value after `std::move` | compiles, reads whatever is left | <span class="ok">error DZ0401</span> |
| Ignoring a returned error | compiles silently | <span class="ok">error DZ0510</span> |

## Safe code, without a borrow checker

The bug C++ code actually has is a reference used after a call grew, shrank or freed the memory it points into: a pointer into a vector kept across a `push_back`, an iterator kept across an `erase`. Dazzle catches it at compile time, without lifetimes. A type names its memory with **ties**, and every function says in its signature which of them a call may end, with a **`kills`** clause:

```dz
// in std's List: each signature says what a call may end
pub fn push(&mut self, v: T) kills self@items      // may move the array
pub fn len(&self) -> usize                         // no clause: kills nothing
```

<Terminal snippet="invalidated" compact />

The compiler checks each clause against its function's body, and `dz fix` writes the clause a body needs. Aliasing stays legal, a `&mut` and a `&` to the same value included, and no struct carries a lifetime parameter.

Ties are one rule of several. Together they make a promise: **a program with no `unsafe` has no undefined behaviour on one thread.** A moved value cannot be used, nothing is dropped twice, every value is initialised, every index is checked, arithmetic is defined, and reading through a raw pointer happens only inside `unsafe`. Where the promise ends is written down too: `unsafe` blocks, the C and C++ a program calls, and threads, which Dazzle does not have yet. [Safety →](/tour/safety/)

## Memory placed by the compiler

The same ties let the compiler choose where memory comes from, so **ordinary code names no allocator**. A value that never leaves the scope that builds it goes in that scope's **region**, released in one step when the scope ends. A returned value is built where the caller keeps it, and anything else goes on the heap. The editor shows where each allocation went, and `dz placements` lists them with the reason. [Ownership →](/tour/ownership/#where-memory-comes-from)

## One clause for everything that can fail

```dz
enum ErrorCode : u32 {
    Empty = 1
}

fn parse_name(text: &str) !-> &str {
    if text.len == 0 {
        return error(ErrorCode::Empty as u32, "a name cannot be empty")
    }
    return text
}

fn main() {
    let name = parse_name("") or "stranger"          // fall back
    println!("hello, {}", name)

    let other = parse_name("") or { e ->             // handle it
        println!("{}:{}: {}", e.location.file, e.location.line, e.message)
        "nobody"
    }
    println!("hello, {}", other)
}
```

<Terminal snippet="fallback" />

There are no exceptions and no `Result<T, E>`. A function that can fail says so in its signature, and the caller handles the failure with one `or` clause. An `Error` is 32 bytes, never allocates, and carries the source location that created it. Forgetting to handle one is a compile error. [Errors →](/tour/errors/)

## Use C and C++ libraries as they are

A few lines of manifest build a library from its own source, or with its own CMake build. libclang reads its header with the same flags the generated code is compiled with. Its declarations become an ordinary Dazzle module, C++ classes and overloaded methods included:

```dz
let mut counter = shp::shapes::Counter(10)    // a C++ class and its constructor
counter.add(5)                                // an overload set, resolved by argument type
shp::shapes::translate(&mut moving, 1, 1)     // `Point&` is a `&mut Point`
```

A function that takes only values is safe to call. One that is handed a pointer is safe once the library's recipe says which of its functions keep a pointer past the call, and those stay `unsafe`. Every example in the gallery above works this way: raylib, SDL3, Box2D, sokol, stb and RGFW, each built from its own source. [C++ interop →](/tour/cpp-interop/)

## Where it fits

You can use Dazzle anywhere you would otherwise reach for C++:

- **Games and engines.** This is where it is furthest along.
- **Embedded and firmware.** There is no runtime and no garbage collector.
- **Tools and native applications.**
- **Real-time code**, where a garbage-collector pause is a bug.
- **An existing C++ codebase**, one module at a time.
