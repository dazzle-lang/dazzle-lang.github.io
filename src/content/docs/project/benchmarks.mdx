How fast is Dazzle compared with C++? Single constructs say little, because an indexed load compiles to the same instruction in both. These are whole programs instead. Each one is written idiomatically in both languages, built by the same compiler at the same optimisation level, and timed from start to finish.

- **A\* search**: 200 searches across a 400×400 grid. It uses a generic binary heap, hash maps keyed by a struct, and allocation in every search.
- **Tokenizer, parser and evaluator**: 100,000 generated statements, about 8 MB of text. Each statement is parsed into a tree of tagged unions and evaluated, and about one in eight fails on purpose, through `!->`.
- **Word count**: 2,000,000 generated words. It counts every distinct word in a hash map, then sorts the counts.

Both halves of each pair print a checksum over their whole result, and a run whose two halves disagree is refused. Each C++ half is written as a C++ reviewer would accept it: `std::vector`, `std::unordered_map`, `std::priority_queue`, `std::string`, `std::unique_ptr` and `std::sort`. Each language uses its own standard library, as benchmarks between languages usually do, so a ratio includes each library's design choices; the note below says where one decides it. The [rules and sources](https://github.com/dazzle-lang/Dazzle/tree/master/tests/bench_programs) are in the repository.

## The latest run

<Benchmarks view="latest" />

<Aside type="note" title="How the gap closed, and what is left">
Every gap the earlier runs showed had a known cause in the standard library or the compiler, not in the language's rules. Between the runs at [aa58e02](https://github.com/dazzle-lang/Dazzle/commit/aa58e02) and [f0a0ab9](https://github.com/dazzle-lang/Dazzle/commit/f0a0ab9) (the runs since changed the build; the latest also made the g++ times faster, below):

- **A\* search:** its hash and comparison functions are inlined, and so are `List`'s index checks ([T-0157](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0157-astar-each-search-hash-maps-regrow.md)), and `HashMap` is a SwissTable: one control byte per slot, read eight at a time ([T-0164](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0164-peak-memory-30-50-over-c.md)). It is now faster than the C++ half, and its peak memory is under it, mostly because of the hash table: Dazzle's is a SwissTable, one array of slots probed eight at a time, where `std::unordered_map` allocates a node per entry. Measured once with Dazzle's map, heap and sort ported line for line into the C++ half, A\* search was even with C++ (1.00× and 1.01×), the parser and evaluator 1.13–1.19× and the word count 1.13–1.29×.
- **The parser and evaluator:** fewer moves through `or return` and a 24-byte `Box`, moved once ([T-0097](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0097-moving-union-through-fallible-result-costs.md)), and its tree nodes, each rebuilt on every pass of a loop, kept in the scope's region ([T-0146](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0146-value-rebuilt-on-each-pass-loop.md)).
- **The word count:** `List::sort_by` is an introsort, where it was a heapsort ([T-0096](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0096-list-sort-by-heapsort-through-function.md)), and a `String` keeps text of up to 15 bytes inside itself, as `std::string` does ([T-0156](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0156-string-always-allocates-short-text-kept.md)).

- **With g++**, every program got faster: g++ now inlines Dazzle's functions as readily as ones declared `inline` ([T-0190](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0190-each-module-defines-instance-methods-it.md)).
- **The parser and evaluator, in the latest run:** `Formatter` appends each piece in place, where it called a function for each, and writes a number's digits without a hardware division per digit, which took the text's generation from 41 ms to 33 ([T-0217](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0217-formatter-writes-each-piece-through-out.md)). And each statement's tree, already in the region of its pass of the loop, is no longer dropped node by node before the region frees it whole ([T-0218](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0218-skip-drop-tree-box-es-in.md)). From 1.17× C++ to 1.05× with clang, and from 1.08× to 0.92× with g++.

In the latest run, A\* search runs at 0.80× C++ with clang and 0.84× with g++, the word count at 0.90× and 0.85×, and the parser and evaluator at 1.05× and 0.92×.

What is left: the parser and evaluator with clang, 5% slower than C++, most of it the destructors run on the values its parser moves out of ([T-0097](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0097-moving-union-through-fallible-result-costs.md)); and the word count's peak memory, about 5 MiB over C++'s, whose cause is not yet measured.

Some of the cost is the language's own, and it stays by design: indexing is bounds-checked in every build, integer arithmetic wraps, and division checks its divisor.
</Aside>

## Build time

Each half is built two ways, three times each, and the median is shown: **from clean**, with nothing built before, and after a **one-line change** to the program, as someone working on it waits for. Both are measured in release, the build whose program the timings above ran, and in debug, `dz build`'s default. For Dazzle, `dz build --timings` says where the time went, phase by phase: Dazzle's own phases, from reading the manifests to emitting the C++; importing C and C++ headers with libclang; and the C++ compiler and the link, on the generated code. The C++ half is a single compiler invocation on one file, so a one-line change compiles all of it again.

<Aside type="note" title="Where the build time goes">
**A build from clean now costs what a one-line change does.** The runtime and the standard library are the same in every program, so they are compiled once per machine, with the standard library's declarations precompiled, and kept in a per-user cache, as a C++ compiler's standard library is built once ([T-0182](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0182-one-compiled-standard-library-shared-by.md)). The import of `stdlib.h` through libclang is kept there too, from 85 ms to 2 ms ([T-0101](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0101-every-build-imports-stdlib-h-with.md)). A release build from clean takes 0.53–0.58 s with clang and 0.70–0.81 s with g++: 1.0–1.3 times the C++ half with clang and 1.6–1.9 times with g++, where before these caches it was 2.2–2.9.

**In debug**, from clean or after a one-line change, a build takes 0.19–0.32 s, against 0.27–0.47 s for the C++ half, which compiles its whole file again: as fast as the C++ half or faster, for every program. **In release** it takes 0.44–0.81 s, since link-time optimisation works on the whole program at the link, and g++ inlines more of it than it did, which makes its programs faster.

Of a debug build, Dazzle's own work, from parsing to emitting the C++, is 65 to 72 ms, from 90 to 100: the ownership check no longer checks the standard library again in every build. The largest parts are now emitting the C++, about 20 ms, and the type check, which still checks the standard library along with the program ([T-0025](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0025-std-type-checked-in-every-analysis.md)). The rest is the C++ compiler and the link on the program's own generated code.

Both targets for 0.2 are met on this machine: a debug rebuild after a one-line change in under 0.5 s, and a release build from clean within twice the C++ half's time ([T-0180](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0180-0-2-build-time-targets-measured.md)).
</Aside>

### At scale

These three programs are a single file each, which is C++'s best case: one compiler invocation and no build system. To see how a build grows, [`tools/bench_scale.py`](https://github.com/dazzle-lang/Dazzle/blob/master/tools/bench_scale.py) generates a project of up to 100 modules, about 510 lines of Dazzle each, with structs, methods, generic containers, enums and calls between modules, and the same program in C++, one header and one source per module. The C++ half is built as `make -j` builds a plain project: each file on its own, all at once, with no precompiled headers. Both halves print the same checksum. Debug, clang, Linux:

| 100 modules, 51,000 lines | Dazzle, first measured | Dazzle now | C++ |
|---|---:|---:|---:|
| From clean | 60 s | 12.2 s | 5.2 s |
| Nothing changed | 8.8 s | 4.8 s | 0.05 s |
| One module changed | 15.2 s | 6.0 s | 1.1 s |

The first measurement found two costs that grew faster than the project. Each module's C++ header carried every method of every generic instance it used, about 1,100 lines for each `List<T>`, and every module above it parsed them again; now each instance's methods are defined once, and a header holds only declarations ([T-0185](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0185-generic-instance-method-bodies-are-in.md)). And deciding which files to compile again read every header each one includes; now it goes by size and time, and the link is skipped when nothing changed ([T-0186](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0186-checking-that-objects-are-up-date.md)).

After a change, the C++ compiler's share of Dazzle's build is now close to the whole C++ build, 1.3 s against 1.1 s. What is left is Dazzle's own work, 4.5 s of every build at 100 modules, which still grows faster than the program: emitting the C++, the ownership and placement checks, and instantiating generics nearly triple each time the project doubles ([T-0187](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0187-dazzle-own-phases-grow-faster-than.md)). Every size and both compilers are in [`SCALE.md`](https://github.com/dazzle-lang/Dazzle/blob/master/tests/bench_programs/SCALE.md).

## Every run

Each run is kept. As the compiler and the standard library improve, this is where the ratios should be seen to fall.

### Adding a run

Run the suite on a quiet machine, from a Dazzle checkout at the commit being measured. Write its JSON into this site's `src/data/benchmarks/`:

```bash
cargo build --release -p dz
python tools/bench_programs.py --json ../dazzle-lang.github.io/src/data/benchmarks/2026-11-30-abc1234.json
```

Then add `date`, `commit` and a one-line `summary` at the top of the file. Runs are only comparable on the same machine and compilers, so a run on new hardware should say so in its summary.
