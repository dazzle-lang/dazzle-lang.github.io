How fast is Dazzle compared with C++? Single constructs say little, because an indexed load compiles to the same instruction in both. These are whole programs instead. Each one is written idiomatically in both languages, built by the same compiler at the same optimisation level, and timed from start to finish.

- **A\* search**: 200 searches across a 400×400 grid. It uses a generic binary heap, hash maps keyed by a struct, and allocation in every search.
- **Tokenizer, parser and evaluator**: 100,000 generated statements, about 8 MB of text. Each statement is parsed into a tree of tagged unions and evaluated, and about one in eight fails on purpose, through `!->`.
- **Word count**: 2,000,000 generated words. It counts every distinct word in a hash map, then sorts the counts.

Both halves of each pair print a checksum over their whole result, and a run whose two halves disagree is refused. Each C++ half is written as a C++ reviewer would accept it: `std::vector`, `std::unordered_map`, `std::priority_queue`, `std::string`, `std::unique_ptr` and `std::sort`. Each language uses its own standard library, as benchmarks between languages usually do, so a ratio includes each library's design choices; the note below says where one decides it. The [rules and sources](https://github.com/dazzle-lang/Dazzle/tree/master/tests/bench_programs) are in the repository.

## The latest run

<Benchmarks view="latest" />

<Aside type="note" title="How the gap closed, and what is left">
Every gap the earlier runs showed had a known cause in the standard library or the compiler, not in the language's rules. Between the previous run and this one:

- **A\* search:** its hash and comparison functions are inlined, and so are `List`'s index checks ([T-0157](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0157-astar-each-search-hash-maps-regrow.md)), and `HashMap` is a SwissTable: one control byte per slot, read eight at a time ([T-0164](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0164-peak-memory-30-50-over-c.md)). It is now faster than the C++ half, and its peak memory is under it, mostly because of the hash table: Dazzle's is a SwissTable, one array of slots probed eight at a time, where `std::unordered_map` allocates a node per entry. Measured once with Dazzle's map, heap and sort ported line for line into the C++ half, A\* search was even with C++ (1.00× and 1.01×), the parser and evaluator 1.13–1.19× and the word count 1.13–1.29×.
- **The parser and evaluator:** fewer moves through `or return` and a 24-byte `Box`, moved once ([T-0097](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0097-moving-union-through-fallible-result-costs.md)), and its tree nodes, each rebuilt on every pass of a loop, kept in the scope's region ([T-0146](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0146-value-rebuilt-on-each-pass-loop.md)).
- **The word count:** `List::sort_by` is an introsort, where it was a heapsort ([T-0096](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0096-list-sort-by-heapsort-through-function.md)), and a `String` keeps text of up to 15 bytes inside itself, as `std::string` does ([T-0156](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0156-string-always-allocates-short-text-kept.md)).

What is left: the parser and evaluator, still 7–17% slower than C++, and the word count's peak memory, about 5 MiB over C++'s, whose cause is not yet measured.

Some of the cost is the language's own, and it stays by design: indexing is bounds-checked in every build, integer arithmetic wraps, and division checks its divisor.
</Aside>

## Build time

Each half is built from clean three times, and the median is shown. For Dazzle, `dz build --timings` says where the time went, phase by phase: Dazzle's own phases, from reading the manifests to emitting the C++; importing C and C++ headers with libclang; and the C++ compiler on the generated code. The C++ half is a single compiler invocation on one file.

<Benchmarks view="build" />

<Aside type="note" title="Where the build time goes">
Dazzle's own work, from parsing to emitting the C++, takes 90 to 100 ms on each of these programs. The largest part is the ownership check, ties included, which checks the standard library again in every build along with the program. Almost all the rest happens outside Dazzle:

- **The C++ compiler**, on the generated code, takes 1.8–1.9 s with clang and 1.4–1.5 s with g++, link-time optimisation included. Most of that is the standard library's C++, which is compiled again in every build ([T-0102](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0102-standard-library-c-compiled-again-in.md)).
- **Importing `stdlib.h`** with libclang takes about 85 ms in this run (380 ms in the first, with clang 23's libclang). The standard library uses it for its heap allocator, so every program pays this, in every build ([T-0101](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0101-every-build-imports-stdlib-h-with.md)).

Both are fixable without changing the language. As they are fixed, this table should show it.
</Aside>

### Adding a run

Run the suite on a quiet machine, from a Dazzle checkout at the commit being measured. Write its JSON into this site's `src/data/benchmarks/`:

```bash
cargo build --release -p dz
python tools/bench_programs.py --json ../dazzle-lang.github.io/src/data/benchmarks/2026-11-30-abc1234.json
```

Then add `date`, `commit` and a one-line `summary` at the top of the file. Runs are only comparable on the same machine and compilers, so a run on new hardware should say so in its summary.
