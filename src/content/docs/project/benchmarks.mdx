How fast is Dazzle compared with C++? Single constructs say little, because an indexed load compiles to the same instruction in both. These are whole programs instead. Each one is written idiomatically in both languages, built by the same compiler at the same optimisation level, and timed from start to finish.

- **A\* search**: 200 searches across a 400×400 grid. It uses a generic binary heap, hash maps keyed by a struct, and allocation in every search.
- **Tokenizer, parser and evaluator**: 100,000 generated statements, about 8 MB of text. Each statement is parsed into a tree of tagged unions and evaluated, and about one in eight fails on purpose, through `!->`.
- **JSON reader and writer**: 100,000 generated records, a 17 MB document. It parses the text into a tree of tagged unions holding strings and lists, reporting errors through `!->`, turns the tree into a list of records, and writes them back out. Dazzle's writer is written once against reflection's type table; the C++ half writes its `to_json` by hand, since C++17 has no reflection.
- **Ray tracer**: a 960×540 image at 16 rays a pixel, with spheres, a checkered floor, soft shadows and mirrors. It is `f32` arithmetic through a vector type's operators, small structs passed and returned by value, a tagged union switched on in the inner loop, and an optional returned from every intersection test.
- **Word count**: 2,000,000 generated words. It counts every distinct word in a hash map, then sorts the counts.

Both halves of each pair print a checksum over their whole result, and a run whose two halves disagree is refused. The ray tracer's checksum is over every byte of the image, so both of its halves are also built with `-ffp-contract=off`, which keeps either compiler from fusing a multiply and an add in one half and not the other. Each C++ half is written as a C++ reviewer would accept it: `std::vector`, `std::unordered_map`, `std::priority_queue`, `std::string` and `std::string_view`, `std::variant`, `std::unique_ptr` and `std::sort`. Each language uses its own standard library, as benchmarks between languages usually do, so a ratio includes each library's design choices; the note below says where one decides it. The [rules and sources](https://github.com/dazzle-lang/Dazzle/tree/master/tests/bench_programs) are in the repository.

## The latest run

<Benchmarks view="latest" />

<Aside type="note" title="How the gap closed, and what is left">
Every gap the earlier runs showed had a known cause in the standard library or the compiler, not in the language's rules. Between the runs at [aa58e02](https://github.com/dazzle-lang/Dazzle/commit/aa58e02) and [f0a0ab9](https://github.com/dazzle-lang/Dazzle/commit/f0a0ab9):

- **A\* search:** its hash and comparison functions are inlined, and so are `List`'s index checks ([T-0157](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0157-astar-each-search-hash-maps-regrow.md)), and `HashMap` is a SwissTable: one control byte per slot, read eight at a time ([T-0164](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0164-peak-memory-30-50-over-c.md)). It is now faster than the C++ half, and its peak memory is under it, mostly because of the hash table: Dazzle's is a SwissTable, one array of slots probed eight at a time, where `std::unordered_map` allocates a node per entry. Measured once with Dazzle's map, heap and sort ported line for line into the C++ half, A\* search was even with C++ (1.00× and 1.01×), the parser and evaluator 1.13–1.19× and the word count 1.13–1.29×.
- **The parser and evaluator:** fewer moves through `or return` and a 24-byte `Box`, moved once ([T-0097](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0097-moving-union-through-fallible-result-costs.md)), and its tree nodes, each rebuilt on every pass of a loop, kept in the scope's region ([T-0146](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0146-value-rebuilt-on-each-pass-loop.md)).
- **The word count:** `List::sort_by` is an introsort, where it was a heapsort ([T-0096](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0096-list-sort-by-heapsort-through-function.md)), and a `String` keeps text of up to 15 bytes inside itself, as `std::string` does ([T-0156](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0156-string-always-allocates-short-text-kept.md)).

The two runs after it changed the build ([below](#build-time)). Then, in the runs at [68ec5ca](https://github.com/dazzle-lang/Dazzle/commit/68ec5ca) and at [ac6e719](https://github.com/dazzle-lang/Dazzle/commit/ac6e719), the latest:

- **With g++**, every program got faster: g++ now inlines Dazzle's functions as readily as ones declared `inline` ([T-0190](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0190-each-module-defines-instance-methods-it.md)).
- **The parser and evaluator:** `Formatter` appends each piece in place, where it called a function for each, and writes a number's digits without a hardware division per digit, which took the text's generation from 41 ms to 33 ([T-0217](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0217-formatter-writes-each-piece-through-out.md)). And each statement's tree, already in the region of its pass of the loop, is no longer dropped node by node before the region frees it whole ([T-0218](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0218-skip-drop-tree-box-es-in.md)). From 1.17× C++ to 1.05× with clang, and from 1.08× to 0.92× with g++. In the latest run a `Box` is one word, where it was three, which took it to 0.87× with g++ ([T-0229](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0229-box-in-one-word-its-allocator.md)).
- **The word count's peak memory**, 38 MiB against C++'s 32, is 34 MiB in the latest run: a `String` or a `List` holds its allocator in one word, where it took two, so each is 32 bytes, as `std::string` is ([T-0228](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0228-one-word-allocator-handle-in-string.md)).
- **The JSON reader and writer** was 1.70× C++ with clang and 1.91× with g++ when it was added, the day before the latest run. Floats are written through `std::to_chars` and parsed through `std::from_chars`, a moved-from value nothing can see is not reset, a `List` moves its elements as bytes, and values move by default, so a parsed string is no longer copied out of the tree ([T-0225](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0225-what-keeps-json-behind-its-c.md), [T-0234](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0234-what-kept-json-raytrace-behind-c.md), [T-0235](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0235-values-move-by-default-clone.md)). It is now 0.99× and 1.06×.
- **The ray tracer** was 1.25× with clang and 1.11× with g++. A module's private functions are now `static` in the generated C++, so a C++ compiler inlines them as it does a C++ program's ([T-0221](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0221-module-private-functions-have-external-linkage.md)). The generated code builds a struct the way a C++ programmer writes it, and assigning an optional no longer builds a temporary one to copy in, which was most of g++'s gap ([T-0222](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0222-empty-optional-builds-its-whole-payload.md)). It is now 1.06× and 0.97×.

In the latest run, A\* search runs at 0.80× C++ with clang and 0.83× with g++, the word count at 0.87× and 0.88×, the parser and evaluator at 1.04× and 0.87×, the JSON reader and writer at 0.99× and 1.06×, and the ray tracer at 1.06× and 0.97×.

What is left:

- **The ray tracer with clang**, 6% slower than C++. No change to the shape of the generated code moved it, so it is most likely the layout of the types: in the C++ half, making its shapes a tagged union laid out as Dazzle's cost 16 ms ([T-0222](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0222-empty-optional-builds-its-whole-payload.md)).
- **The JSON reader and writer with g++**, 6% slower. About 10 ms of it is the benchmark's own: Dazzle's writer goes through reflection's type table, and the C++ half's is written by hand. The rest is writing floats as text and the results built by every fallible return ([T-0225](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0225-what-keeps-json-behind-its-c.md)). Its peak memory is 4% over C++'s.
- **The parser and evaluator with clang**, 4% slower, most of it the destructors run on the values its parser has moved out of ([T-0231](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0231-moved-from-value-drop-called-though.md)).

The language's safety does not explain any of these. With every bounds check and panic compiled out of the generated C++, and the flags that define integer overflow, aliasing and endless loops turned off, neither the JSON reader and writer nor the ray tracer ran faster with either compiler ([T-0234](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0234-what-kept-json-raytrace-behind-c.md)). Those costs stay by design all the same: indexing is bounds-checked in every build, integer arithmetic wraps, and division checks its divisor.
</Aside>

## Build time

Each half is built two ways, three times each, and the median is shown: **from clean**, with nothing built before, and after a **one-line change** to the program, as someone working on it waits for. Both are measured in release, the build whose program the timings above ran, and in debug, `dz build`'s default. For Dazzle, `dz build --timings` says where the time went, phase by phase: Dazzle's own phases, from reading the manifests to emitting the C++; importing C and C++ headers with libclang; and the C++ compiler and the link, on the generated code. The C++ half is a single compiler invocation on one file, so a one-line change compiles all of it again.

<Aside type="note" title="Where the build time goes">
**A build from clean now costs what a one-line change does.** The runtime and the standard library are the same in every program, so they are compiled once per machine, with the standard library's declarations precompiled, and kept in a per-user cache, as a C++ compiler's standard library is built once ([T-0182](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0182-one-compiled-standard-library-shared-by.md)). The import of `stdlib.h` through libclang is kept there too, from 85 ms to 2 ms ([T-0101](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0101-every-build-imports-stdlib-h-with.md)). A release build from clean takes 0.35–0.96 s with clang and 0.46–1.09 s with g++: 0.9–1.3 times the C++ half with clang and 1.3–1.8 times with g++, where before these caches it was 2.2–2.9. The JSON reader and writer takes longest, at 0.96 s and 1.09 s, against 0.72 s and 0.70 s for its C++ half.

**In debug**, from clean or after a one-line change, a build takes 0.16–0.32 s, against 0.25–0.47 s for the C++ half, which compiles its whole file again: as fast as the C++ half or faster, for every program. **In release** it takes 0.33–1.09 s, since link-time optimisation works on the whole program at the link, and g++ inlines more of it than it did, which makes its programs faster.

Of a debug build from clean, Dazzle's own work, from parsing to emitting the C++, is 57 to 69 ms, from 90 to 100 before the ownership check stopped checking the standard library again in every build. The largest parts are emitting the C++, about 20 ms, and the type check, about 14 ms, which still checks the standard library along with the program ([T-0025](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0025-std-type-checked-in-every-analysis.md)). The rest is the C++ compiler and the link on the program's own generated code.

Both targets for 0.2 are met on this machine: a debug rebuild after a one-line change in under 0.5 s, and a release build from clean within twice the C++ half's time ([T-0180](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0180-0-2-build-time-targets-measured.md)).
</Aside>

### At scale

These five programs are a single file each, which is C++'s best case: one compiler invocation and no build system. To see how a build grows, [`tools/bench_scale.py`](https://github.com/dazzle-lang/Dazzle/blob/master/tools/bench_scale.py) generates a project of up to 100 modules, about 510 lines of Dazzle each, with structs, methods, generic containers, enums and calls between modules, and the same program in C++, one header and one source per module. The C++ half is built as `make -j` builds a plain project: each file on its own, all at once, with no precompiled headers. Both halves print the same checksum. Debug, clang, Linux:

| 100 modules, 51,000 lines | Dazzle, first measured | Dazzle now | C++ |
|---|---:|---:|---:|
| From clean | 60 s | 8.2 s | 5.2 s |
| Nothing changed | 8.8 s | 0.01 s | 0.05 s |
| One module changed | 15.2 s | 0.88 s | 1.1 s |

After a one-line change, Dazzle now builds faster than `make` at every size measured: 0.25 s against 0.39 s at 10 modules, 0.35 s against 0.50 s at 25, 0.52 s against 0.69 s at 50. That holds whether the changed module is a leaf or the root that every other module depends on.

The first measurement found two costs that grew faster than the project. Each module's C++ header carried every method of every generic instance it used, about 1,100 lines for each `List<T>`, and every module above it parsed them again; now each instance's methods are defined once, and a header holds only declarations ([T-0185](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0185-generic-instance-method-bodies-are-in.md)). And deciding which files to compile again read every header each one includes; now it goes by size and time, and the link is skipped when nothing changed ([T-0186](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0186-checking-that-objects-are-up-date.md)).

Since then, builds have become incremental. A build with nothing changed checks a stamp and skips analysis ([T-0192](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0192-build-with-nothing-changed-skips-analysis.md)). An edit re-runs ownership, instantiation and code generation only for the modules it can affect, and an edit inside a function body leaves the modules above it alone ([T-0197](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0197-edit-re-runs-ownership-instantiation-emission.md), [T-0198](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0198-body-only-edit-module-others-depend.md)). The standard library's generated C++ is kept between builds too, and the C++ compiler is asked its version once rather than on every build ([T-0025](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0025-std-type-checked-in-every-analysis.md)).

From clean, the C++ compiler and the link take 5.9 s of Dazzle's 8.2 s, a module's generated files compiled as one where there are more files than cores ([T-0199](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0199-clean-build-at-scale-parses-every.md)). After an edit, the C++ compiler takes 0.2 s. Most of what is left, 0.63 s, is Dazzle's own front end, which still reads the whole program on every build. Every size is in [`SCALE.md`](https://github.com/dazzle-lang/Dazzle/blob/master/tests/bench_programs/SCALE.md), which also says what changed between runs.

## Every run

Each run is kept. As the compiler and the standard library improve, this is where the ratios should be seen to fall.

### Adding a run

Run the suite on a quiet machine, from a Dazzle checkout at the commit being measured. Write its JSON into this site's `src/data/benchmarks/`:

```bash
cargo build --release -p dz
python tools/bench_programs.py --json ../dazzle-lang.github.io/src/data/benchmarks/2026-11-30-abc1234.json
```

Then add `date`, `commit` and a one-line `summary` at the top of the file. Runs are only comparable on the same machine and compilers, so a run on new hardware should say so in its summary.
