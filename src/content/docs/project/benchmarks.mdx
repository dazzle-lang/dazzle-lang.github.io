How fast is Dazzle compared with C++? Single constructs say little, because an indexed load compiles to the same instruction in both. These are whole programs instead. Each one is written idiomatically in both languages, built by the same compiler at the same optimisation level, and timed from start to finish.

- **A\* search**: 200 searches across a 400×400 grid. It uses a generic binary heap, hash maps keyed by a struct, and allocation in every search.
- **Tokenizer, parser and evaluator**: 100,000 generated statements, about 8 MB of text. Each statement is parsed into a tree of tagged unions and evaluated, and about one in eight fails on purpose, through `!->`.
- **Word count**: 2,000,000 generated words. It counts every distinct word in a hash map, then sorts the counts.

Both halves of each pair print a checksum over their whole result, and a run whose two halves disagree is refused. Each C++ half is written as a C++ reviewer would accept it: `std::vector`, `std::unordered_map`, `std::priority_queue`, `std::string`, `std::unique_ptr` and `std::sort`. The [rules and sources](https://github.com/dazzle-lang/Dazzle/tree/master/tests/bench_programs) are in the repository.

<Aside type="note" title="Why Dazzle is slower today">
The gap comes from known, specific places in the standard library and the compiler, not from the language's rules. Each one is a task with its measurement:

- **The parser and evaluator:** returning a tree node through `!->` costs extra moves and a drop at every step, about a sixth of the program's time, and `Box` is five times the size of `unique_ptr` ([T-0097](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0097-moving-union-through-fallible-result-costs.md)). And its tree nodes are on the heap: the compiler puts a value in a scope's region when it can prove the value stays there, but a value rebuilt on every pass of a loop, as each node is, keeps the heap ([T-0146](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0146-value-rebuilt-on-each-pass-loop.md)).
- **The word count:** `List::sort_by` is a heapsort called through a function pointer; when first measured it took 100 ms where `std::sort` took 19 ([T-0096](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0096-list-sort-by-heapsort-through-function.md)). And a `String` always allocates, where `std::string` keeps text of up to 15 bytes inside itself, as every word here is ([T-0156](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0156-string-always-allocates-short-text-kept.md)).
- **A\* search:** each search's hash maps start empty and regrow about eleven times, and its hash and comparison functions are called rather than inlined ([T-0157](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0157-astar-each-search-hash-maps-regrow.md)).

Some of the cost is the language's own, and it stays by design: indexing is bounds-checked in every build, and integer arithmetic wraps.
</Aside>

## Build time

Each half is built from clean three times, and the median is shown. For Dazzle, `dz build --timings` says where the time went, phase by phase: Dazzle's own phases, from reading the manifests to emitting the C++; importing C and C++ headers with libclang; and the C++ compiler on the generated code. The C++ half is a single compiler invocation on one file.

<Benchmarks view="build" />

<Aside type="note" title="Where the build time goes">
Dazzle's own work, from parsing to emitting the C++, takes about 90 ms on each of these programs. The largest part is the ownership check, ties included, which checks the standard library again in every build along with the program. Almost all the rest happens outside Dazzle:

- **The C++ compiler**, on the generated code, takes 1.8–2.2 s with clang and 1.3–1.5 s with g++, link-time optimisation included. Most of that is the standard library's C++, which is compiled again in every build ([T-0102](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0102-standard-library-c-compiled-again-in.md)).
- **Importing `stdlib.h`** with libclang takes about 85 ms in this run (380 ms in the first, with clang 23's libclang). The standard library uses it for its heap allocator, so every program pays this, in every build ([T-0101](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0101-every-build-imports-stdlib-h-with.md)).

Both are fixable without changing the language. As they are fixed, this table should show it.
</Aside>

### Adding a run

Run the suite on a quiet machine, from a Dazzle checkout at the commit being measured. Write its JSON into this site's `src/data/benchmarks/`:

```bash
cargo build --release -p dz
python tools/bench_programs.py --json ../dazzle-lang.github.io/src/data/benchmarks/2026-11-30-abc1234.json
```

Then add `date`, `commit` and a one-line `summary` at the top of the file. Runs are only comparable on the same machine and compilers, so a run on new hardware should say so in its summary.
