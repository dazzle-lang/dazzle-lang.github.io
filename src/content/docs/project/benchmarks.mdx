How fast is Dazzle compared with C++? Single constructs say little, because an indexed load compiles to the same instruction in both. These are whole programs instead. Each one is written idiomatically in both languages, built by the same compiler at the same optimisation level, and timed from start to finish.

- **A\* search**: 200 searches across a 400×400 grid. It uses a generic binary heap, hash maps keyed by a struct, and allocation in every search.
- **A battle on an ECS library**: 600 units in two teams for 100 steps, on a small entity-component-system library of its own, which a game uses by making a `World` and registering systems. Each step moves every unit, pushes apart those that overlap with a query inside a query over the same storages, lets each unit strike the nearest enemy, writing another unit's health, and replaces the dead. It is written in Rust too, [three ways](#three-languages).
- **Tokenizer, parser and evaluator**: 100,000 generated statements, about 8 MB of text. Each statement is parsed into a tree of tagged unions and evaluated, and about one in eight fails on purpose, through `!->`.
- **JSON reader and writer**: 100,000 generated records, a 17 MB document. It parses the text into a tree of tagged unions holding strings and lists, reporting errors through `!->`, turns the tree into a list of records, and writes them back out. Dazzle's writer is written once against reflection's type table; the C++ half writes its `to_json` by hand, since C++17 has no reflection.
- **Ray tracer**: a 960×540 image at 16 rays a pixel, with spheres, a checkered floor, soft shadows and mirrors. It is `f32` arithmetic through a vector type's operators, small structs passed and returned by value, a tagged union switched on in the inner loop, and an optional returned from every intersection test.
- **Word count**: 2,000,000 generated words. It counts every distinct word in a hash map, then sorts the counts.

Both halves of each pair print a checksum over their whole result, and a run whose two halves disagree is refused. The ray tracer's checksum is over every byte of the image and the battle's over every surviving unit's position, so both of their halves are also built with `-ffp-contract=off`, which keeps either compiler from fusing a multiply and an add in one half and not the other. Each C++ half is written as a C++ reviewer would accept it: `std::vector`, `std::unordered_map`, `std::priority_queue`, `std::string` and `std::string_view`, `std::variant`, `std::unique_ptr` and `std::sort`. Each language uses its own standard library, as benchmarks between languages usually do, so a ratio includes each library's design choices; the note below says where one decides it. The [rules and sources](https://github.com/dazzle-lang/Dazzle/tree/master/tests/bench_programs) are in the repository.

- **The battle on an ECS library** was added, and was 1.35× C++ with clang and 1.41× with g++ the same day. Two things were most of it, neither the bounds checks ([T-0240](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0240-ecs-dazzle-1-35-1-41x.md)). With g++, the function a failing bounds check calls was not declared `[[noreturn]]`, so after every check g++ assumed it had returned having changed memory. It is now 0.70× and 1.01×.
- **The JSON reader and writer:** a moved-from value is no longer destroyed where nothing could see it ([T-0231](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0231-moved-from-value-drop-called-though.md)), and the standard library's `#[inline]` functions are inlined at every call. From 0.99× and 1.06× to 0.92× and 1.01×.
- **A\* search with g++** went from 0.83× to 0.89× with `[[noreturn]]`, though it runs fewer instructions: g++ laid its code out differently.

In the latest run, A\* search runs at 0.78× C++ with clang and 0.89× with g++, the battle at 0.70× and 1.01×, the word count at 0.86× and 0.87×, the parser and evaluator at 0.97× and 0.87×, the JSON reader and writer at 0.92× and 1.01×, and the ray tracer at 1.05× and 0.95×.

What is left:

- **The ray tracer with clang**, 5% slower than C++. No change to the shape of the generated code moved it, so it is most likely the layout of the types: in the C++ half, making its shapes a tagged union laid out as Dazzle's cost 16 ms ([T-0222](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0222-empty-optional-builds-its-whole-payload.md)).
- **The parser and evaluator with clang**, 3% slower, not broken down since its moved-from values stopped being destroyed ([T-0231](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0231-moved-from-value-drop-called-though.md)).
- **The battle with g++**, level with C++; what is left of it is the bounds checks, which the C++ half does not make.

Apart from the battle's, the language's safety does not explain these. With every bounds check and panic compiled out of the generated C++, and the flags that define integer overflow, aliasing and endless loops turned off, neither the JSON reader and writer nor the ray tracer ran faster with either compiler ([T-0234](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0234-what-kept-json-raytrace-behind-c.md)). Those costs stay by design all the same: indexing is bounds-checked in every build, integer arithmetic wraps, and division checks its divisor.

## Three languages

The battle is two things in each language: a small entity-component-system library, and a game that uses it. The library is the same design in all three: an entity is a slot and a generation, each component type has a sparse set found by the type's id in a map, a query walks the smaller of two storages and probes the other, and a resource is a component of the world's own entity. No ECS library from outside is used, since the comparison is between languages and a library's own design would decide the numbers ([T-0172](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0172-ecs-benchmark-against-rust-c-query.md)).

Two of the game's systems are why it exists. One nests a query inside a query over the same two storages and writes both units' velocities; the other walks positions and writes another unit's health. In Dazzle both are written directly: writing through a view moves nothing, so two views of one storage may be live at once, while a `spawn` or `despawn` inside either loop would move a storage, and is refused at compile time. C++ allows both, the unsafe one included. Rust allows neither, so its half is written three ways, each timed:

| Rust version | How the two systems are written |
|---|---|
| `collect` | the nested queries borrow the world shared; what they decide is gathered into a list and written after the loops. The usual answer in Rust |
| `disjoint` | the storages a system needs are taken at once, and the loops walk rows by index, taking two velocities at once with `get_disjoint_mut` where one unit writes another's |
| `cell` | velocity and health are stored as `Cell`s, so every query borrows the world shared and nests as in Dazzle; a write is a `get` and a `set` |

Dazzle takes about half the time of the two versions that keep the nested queries' shape, and 1.12–1.15× the one written as index loops, which gives that shape up. The Rust half is built with `cargo build --release` at `opt-level = 2`, with whole-program LTO and `panic = "abort"`, as the C++ half is built without exceptions. Both Dazzle and Rust check every index; C++ checks none.

## Build time

Each half is built two ways, three times each, and the median is shown: **from clean**, with nothing built before, and after a **one-line change** to the program, as someone working on it waits for. Both are measured in release, the build whose program the timings above ran, and in debug, `dz build`'s default. For Dazzle, `dz build --timings` says where the time went, phase by phase: Dazzle's own phases, from reading the manifests to emitting the C++; importing C and C++ headers with libclang; and the C++ compiler and the link, on the generated code. The C++ half is a single compiler invocation on one file, so a one-line change compiles all of it again.

<Aside type="note" title="Where the build time goes">
**A build from clean now costs what a one-line change does.** The runtime and the standard library are the same in every program, so they are compiled once per machine, with the standard library's declarations precompiled, and kept in a per-user cache, as a C++ compiler's standard library is built once ([T-0182](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0182-one-compiled-standard-library-shared-by.md)). The import of `stdlib.h` through libclang is kept there too, from 85 ms to 2 ms ([T-0101](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0101-every-build-imports-stdlib-h-with.md)). A release build from clean takes 0.34–1.11 s with clang and 0.45–1.30 s with g++: 0.9–1.5 times the C++ half with clang and 1.5–1.7 times with g++, where before these caches it was 2.2–2.9. The battle takes longest, at 1.11 s and 1.30 s, against 0.74 s and 0.78 s for its C++ half: it is two modules, a library and a game, so twice the generated files to compile.

**In debug**, after a one-line change, a build takes 0.16–0.33 s, against 0.25–0.59 s for the C++ half, which compiles its whole file again: faster than the C++ half for every program. From clean it takes 0.18–0.36 s, as fast as the C++ half or faster, except for the battle, two modules, at 0.60 s and 0.72 s against 0.51 s and 0.59 s. **In release** it takes 0.33–1.09 s, since link-time optimisation works on the whole program at the link, and g++ inlines more of it than it did, which makes its programs faster.

Of a debug build from clean, Dazzle's own work, from parsing to emitting the C++, is 57 to 73 ms, from 90 to 100 before the ownership check stopped checking the standard library again in every build. The battle's is 166 ms, most of it the ownership check, 73 ms against the other programs' 10, which is not yet explained. The largest parts are emitting the C++, about 20 ms, and the type check, about 14 ms, which still checks the standard library along with the program ([T-0025](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0025-std-type-checked-in-every-analysis.md)). The rest is the C++ compiler and the link on the program's own generated code.

Both targets for 0.2 are met on this machine: a debug rebuild after a one-line change in under 0.5 s, and a release build from clean within twice the C++ half's time ([T-0180](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0180-0-2-build-time-targets-measured.md)).
</Aside>

### At scale

These programs are small, a single file each but for the battle's two modules, which is C++'s best case: one compiler invocation and no build system. To see how a build grows, [`tools/bench_scale.py`](https://github.com/dazzle-lang/Dazzle/blob/master/tools/bench_scale.py) generates a project of up to 100 modules, about 510 lines of Dazzle each, with structs, methods, generic containers, enums and calls between modules, and the same program in C++, one header and one source per module. The C++ half is built as `make -j` builds a plain project: each file on its own, all at once, with no precompiled headers. Both halves print the same checksum. Debug, clang, Linux:

| 100 modules, 51,000 lines | Dazzle, first measured | Dazzle now | C++ |
|---|---:|---:|---:|
| From clean | 60 s | 8.2 s | 5.2 s |
| Nothing changed | 8.8 s | 0.01 s | 0.05 s |
| One module changed | 15.2 s | 0.88 s | 1.1 s |

After a one-line change, Dazzle now builds faster than `make` at every size measured: 0.25 s against 0.39 s at 10 modules, 0.35 s against 0.50 s at 25, 0.52 s against 0.69 s at 50. That holds whether the changed module is a leaf or the root that every other module depends on.

The first measurement found two costs that grew faster than the project. Each module's C++ header carried every method of every generic instance it used, about 1,100 lines for each `List<T>`, and every module above it parsed them again; now each instance's methods are defined once, and a header holds only declarations ([T-0185](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0185-generic-instance-method-bodies-are-in.md)). And deciding which files to compile again read every header each one includes; now it goes by size and time, and the link is skipped when nothing changed ([T-0186](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0186-checking-that-objects-are-up-date.md)).

Since then, builds have become incremental. A build with nothing changed checks a stamp and skips analysis ([T-0192](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0192-build-with-nothing-changed-skips-analysis.md)). An edit re-runs ownership, instantiation and code generation only for the modules it can affect, and an edit inside a function body leaves the modules above it alone ([T-0197](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0197-edit-re-runs-ownership-instantiation-emission.md), [T-0198](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0198-body-only-edit-module-others-depend.md)). The standard library's generated C++ is kept between builds too, and the C++ compiler is asked its version once rather than on every build ([T-0025](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0025-std-type-checked-in-every-analysis.md)).

From clean, the C++ compiler and the link take 5.9 s of Dazzle's 8.2 s, a module's generated files compiled as one where there are more files than cores ([T-0199](https://github.com/dazzle-lang/Dazzle/blob/master/docs/tasks/T-0199-clean-build-at-scale-parses-every.md)). After an edit, the C++ compiler takes 0.2 s. Most of what is left, 0.63 s, is Dazzle's own front end, which still reads the whole program on every build. Every size is in [`SCALE.md`](https://github.com/dazzle-lang/Dazzle/blob/master/tests/bench_programs/SCALE.md), which also says what changed between runs.

### Adding a run

Run the suite on a quiet machine, from a Dazzle checkout at the commit being measured. Write its JSON into this site's `src/data/benchmarks/`:

```bash
cargo build --release -p dz
python tools/bench_programs.py --json ../dazzle-lang.github.io/src/data/benchmarks/2026-11-30-abc1234.json
```

It needs `cargo` on the path for the battle's Rust half, which the JSON holds under `rust`. Then add `date`, `time`, `commit` and a one-line `summary` at the top of the file. Runs are only comparable on the same machine and compilers, so a run on new hardware should say so in its summary.
