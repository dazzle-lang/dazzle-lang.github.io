`main` owns a list of notices. `show_preview` makes its own short-lived list. Both call `add_notice` to push the same text into their list.

## Follow the call

<ProofExample name="list-regions" showOutput={false} />

Each list is owned by a local variable. Dazzle puts its backing storage in a **region**, a pool of memory it can reclaim together when the owning function returns. When `add_notice` constructs a string, it uses the region of the list passed to that call. The message is long enough to need its own text allocation.

`show_preview` returns first and its region’s storage is reclaimed. `main` can still print `notices[0]` because its region is still alive. Dazzle runs the destructors the values need before reclaiming each region.

## When the receipt leaves checkout

In a separate example, a checkout function files a receipt in a register it was lent. The register can outlive that call. In this example, the compiler chooses the heap for the receipt from the start. `move(receipt)` gives the register ownership of the existing block. `main` can read it after checkout returns.

## How signatures describe the transfer

`file_receipt` declares `sends receipt to register`. That clause tells callers that the register may keep what `receipt` owns. The compiler checks the clause against the function body and uses it when it checks allocation placement. [See the compiler explain and fix the missing clause](/tour/tooling/#fix-a-missing-transfer-clause).

A value’s **home** (`@home`) is the region or heap that supplies its backing memory. A move keeps that memory in place. A function that returns an already-allocated input can declare `in receipt@home` to tell its caller where the result’s memory still lives. These contracts were added in [D-0097, revision r119](/decisions/d-0097-homes-ownership-that-travels-with-its/).

## Inspecting allocations

Run `dz placements` in a project or look at the editor’s inlay hints to see where each allocation goes and why. Use `dz placements --format=json` to read the report in a script. A runtime profiler measures how often those allocations occur and how much memory the program uses.
